# Plan: P2P LAN sync (whole-app device clone)

**Status:** completed

## What the user wants

Copy **everything** from ContactSphere on one phone to ContactSphere on another
phone, over the local Wi-Fi, with no server and no internet. "Everything" means:
contacts and all their details, relationships, favorites, groups, call logs,
interactions, reminders, official details, social links, tags, flagged (blocked/
spam) numbers, the Self contact, secret contacts, and app settings.

The design is ported from the attached `p2p-sync-implementation-guide.md`
(pairing-code + AES-GCM at the payload layer, plain TCP socket on the LAN).

## Decisions already made (with the user)

1. **Sync mode = Mirror / full replace.** The receiving phone's whole app
   database is wiped and replaced with an exact clone of the sender's. Row ids
   are preserved, so every foreign key (relationships, groups, call logs, …)
   stays consistent with no id-remapping. One-way: the phone that **has** the
   data hosts and pushes; the **new** phone connects and receives.
2. **Media files:**
   - **Photos and calling-card images** — their file **bytes are bundled** in the
     sync and rewritten into the new phone's app storage; paths are fixed up.
   - **Ringtone files** — **bytes are NOT sent.** The sender's ringtone *path* is
     copied as-is; on the new phone the tone is used **only if a file already
     exists at that same path**, otherwise the ringtone is left empty (no sound
     ringtone). No audio bytes ever cross the wire.
3. **Secret contacts are included.** This is a deliberate device-to-device clone
   behind biometric auth and a ~320-bit code, so a full copy (secrets included)
   is the point. The whole flow is gated behind `AuthService` (biometric),
   exactly as secret-contact access already is.

## Things that are device-specific and will NOT be copied blindly (with reasons)

These are copied from the source DB but are meaningless or harmful on another
phone, so the import step clears/skips them:

- **`contacts.device_id` and the whole `merged_device_ids` table** — these link
  to the *source phone's* device address book, which is a different set of ids on
  the new phone. Copying them risks mislinking during the existing device-contacts
  sync. On import we set `device_id = NULL` and do **not** restore
  `merged_device_ids`; the new phone re-links to its own device book on its next
  device sync (existing behaviour).
- **SIM-account-keyed settings** — `default_sim_id`, `per_sim_ringtones`,
  `per_sim_colors` are keyed by the *source phone's* SIM phone-account ids, which
  never match the new phone's SIMs. These three keys are **not** synced. All other
  settings (theme, both accents, post-call feedback, dialer top source, default
  country, include-secret-in-export, block/caller-id/spam toggles, ringer volume
  and vibrate, quick replies) **are** synced.

- **SIM mismatch (e.g. 2-SIM source → 1-SIM destination)** — handled by the two
  points above: because the SIM *preferences* are not synced, the destination
  keeps its own SIM setup and never gets a "default SIM" pointing at a SIM it
  lacks. `call_logs.sim_id` / `sim_label` *do* copy (they are the history of
  which SIM each past call used on the old phone) but are **display-only** in
  Recents and are never used to place a new call. `ask_sim_before_call` syncs but
  the SIM picker only shows with 2+ SIMs, so it is inert on a 1-SIM phone.
  **Decision: keep the historical SIM labels as-is** (honest history); blanking
  them on import is a trivial follow-up if the stale labels are unwanted.

## Safety rails ported from the guide (kept as-is)

- Pairing code is high-entropy (64 chars × 31-symbol alphabet ≈ 320 bits),
  generated per session, shown on the host, typed on the client. **It never
  crosses the socket.**
- PBKDF2-HMAC-SHA256 (120k iters, 256-bit key, 16-byte per-session salt) →
  AES-GCM (12-byte IV, 128-bit tag). Salt sent in clear; payload is
  authenticated-encrypted. Wrong code → wrong key → GCM tag fails → abort. No
  fallback cipher.
- Bounded line reads (4 KB handshake cap; large cap per media frame), 30 s socket
  timeout, and validation caps (max rows per table, max field length) applied
  **before** anything is written to the DB.
- **Schema-version guard:** the payload carries the sender's DB `version` (16
  today). If it does not equal the receiver's DB version, the sync aborts with a
  clear "update both phones to the same app version" message, so we never try to
  load rows into a mismatched schema.

## Wire protocol (per session, line-based, all frames after the salt are encrypted)

```
HOST (source)                                CLIENT (new phone)
  ServerSocket.accept() on 8243
  send Base64(salt) in clear  ───────────▶   derive key from (code, salt)
  derive key from (code, salt)
                              ◀──────────    send encrypt("HELLO_SYNC")
  decrypt == "HELLO_SYNC"? no → DENIED+abort
  send encrypt("ACCEPT_SYNC") ───────────▶   decrypt == "ACCEPT_SYNC"? else abort
  send encrypt(META json)     ───────────▶   decrypt META (db rows + settings + file manifest)
  for each file in manifest:
    send encrypt(base64 bytes)───────────▶   read exactly manifest.length file frames
                                             wipe DB + restore rows/settings/files
```

`META` = JSON: `{ schema:1, dbVersion:16, tables:{ contacts:[...], phone_numbers:[...], ... },
settings:{...}, files:[{ref, ext, len}] }`. Media bytes are streamed one encrypted
frame per file (photos + calling cards only), keeping each line bounded and
supporting large books without a giant single line.

## Files to change / create

### New

1. **`lib/services/p2p_sync_service.dart`** — the engine. Crypto block
   (constants, `generatePairingCode`, `normalizeCode`, `deriveKey`, `encrypt`,
   `decrypt`, `readBoundedLine`), host server (`startHost`/`stopHost`), client
   (`connectAndSync`), local-IPv4 discovery via `NetworkInterface.list()`, and a
   `ChangeNotifier`-based `SyncState` (Idle / Hosting(ip, code) / Connecting /
   Syncing(progress) / Completed(counts) / Error(message)) that the UI listens to.
2. **`lib/services/sync_bundle_service.dart`** — builds and applies the payload:
   - `exportBundle()` — dump every synced table to maps, gather synced settings,
     read photo + calling-card file bytes, produce META + file list.
   - `applyBundle()` — inside one transaction with `foreign_keys = OFF`: validate
     caps, write incoming media files to app storage, `DELETE FROM` every table,
     bulk-insert all rows with explicit ids (photos/cards repointed to new local
     paths; ringtone path kept only if a file exists there; `device_id` nulled),
     fix `sqlite_sequence` to each table's max id, commit, re-enable FK, restore
     settings into SharedPreferences, and refresh native mirrors (ringtone /
     screening) + `AppSettings.load()`.
3. **`lib/screens/p2p_sync_screen.dart`** — UI with two modes:
   - **Send to a new phone (host):** shows this phone's IP + the grouped pairing
     code (8-char chunks) with a copy button; waits, then shows progress/result.
   - **Receive from my old phone (client):** fields for host IP + code; a clear
     "this will replace everything in ContactSphere on this phone" confirmation
     before it runs; then progress/result.
   Whole screen entered only after an `AuthService` biometric check (secrets are
   included).

### Edited

4. **`pubspec.yaml`** — add `cryptography: ^2.7.0` (pure-Dart PBKDF2 + AES-GCM;
   Dart has no built-in AES-GCM). Run `flutter pub get`.
5. **`android/app/src/main/AndroidManifest.xml`** — add the LAN permissions the
   app does not have yet: `INTERNET`, `ACCESS_NETWORK_STATE`, `ACCESS_WIFI_STATE`,
   `CHANGE_WIFI_STATE`.
6. **Entry point** — add a "Transfer to another phone" card to the Settings
   screen (and/or the contacts-list overflow menu) that opens
   `p2p_sync_screen.dart`.
7. **`docs/architecture.md`** and **`docs/known-gaps.md`** — document the new P2P
   sync feature (a short section like the existing BLE-exchange one).

### Tests (new)

8. **`test/p2p_crypto_test.dart`** — encrypt→decrypt round-trip; wrong code fails
   to decrypt; `normalizeCode` matches the grouped display; pairing-code length/
   alphabet. (No DB — safe to run with other tests.)
9. **`test/p2p_bundle_test.dart`** — export→apply round-trip on an in-memory
   sqflite DB: seed contacts + children + settings, bundle, wipe, apply, assert
   every table and id matches, `device_id` cleared, ringtone-path rule honored,
   validation caps reject an over-cap payload. **Its own file** (sqlite-backed
   tests must run one file per invocation — known native-assets crash otherwise).

## Order of work

1. Add dependency + manifest permissions; `flutter pub get`.
2. Crypto + engine (`p2p_sync_service.dart`) + its unit test.
3. Bundle export/apply (`sync_bundle_service.dart`) + its round-trip test.
4. UI screen + Settings entry point + biometric gate.
5. `flutter analyze`, run both test files (separately), then the change log.

## Out of scope for this version (call out, not building now)

- **Merge** semantics (keeping the receiver's own data). This version is
  full-replace only.
- **Two-way** sync. One-way push only (host → client).
- **mDNS/NSD auto-discovery.** The user reads the host IP off the screen, as in
  the guide.
- **Ringtone audio transfer.** By the user's decision, only the path is copied.
