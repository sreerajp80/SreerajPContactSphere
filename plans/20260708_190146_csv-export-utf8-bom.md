# Fix: CSV export shows mojibake in Excel/Sheets (missing UTF-8 BOM)

**Status:** completed

## The issue

The user wants to be sure "all data are in Unicode and export/import won't cause any
issues." The vCard export path already handles this (external `.vcf` files use vCard 2.1
with `CHARSET=UTF-8;ENCODING=QUOTED-PRINTABLE` — see the completed plan
`20260707_205712_vcard-unicode-mojibake-export.md`). The **CSV export** is the remaining gap.

`ExportImportService._writeAndShareCsv` builds the file with `Csv().encode(rows)`
(`lib/services/export_import_service.dart:93`). The default `Csv()` adds **no UTF-8 BOM**.
`File.writeAsString` then writes the string as UTF-8 (Dart's default), so the bytes are valid
UTF-8 — but with no BOM.

When such a file is opened in Excel or Google Sheets on Windows, those tools do not detect
UTF-8 and fall back to the system ANSI code page (e.g. Windows-1252). Non-ASCII names
(Devanagari, accented Latin, etc.) then render as mojibake. This is the same class of bug as
the vCard one, in the CSV file.

### Why import is not affected

- The app reads CSV with `XFile.readAsString()` (UTF-8) and decodes with `Csv().decode(...)`.
- The `csv` 8.0.0 decoder strips a leading UTF-8 BOM (`_checkBOMAndSep` in
  `csv_decoder.dart`), so adding a BOM to our own exports does **not** break the app's
  re-import — and the header row is skipped anyway.

## The fix

In `_writeAndShareCsv`, encode with a UTF-8 BOM:

```dart
final csv = Csv(addBom: true).encode(rows);
```

- Keeps the comma field delimiter (do **not** use `Csv.excel()`, which switches to a `;`
  delimiter — our phone/email cells already use `;` internally as a pair separator).
- `addBom: true` prepends `﻿`, which `writeAsString` encodes as the 3-byte UTF-8 BOM
  `EF BB BF`. Excel/Sheets then read the file as UTF-8 and show Unicode names correctly.

## Files to change

1. **`lib/services/export_import_service.dart`**
   - Line ~93: change `Csv().encode(rows)` to `Csv(addBom: true).encode(rows)`.
   - Update the doc comment on `_writeAndShareCsv` to note the BOM is written for
     cross-tool (Excel/Sheets) Unicode compatibility.

2. **`test/` (new or existing export/import test)**
   - Add a small host-side test that encodes a row containing a non-ASCII name with
     `Csv(addBom: true)` and asserts the result starts with `﻿` and that
     `Csv().decode(...)` round-trips the row back without the BOM leaking into the data.
   - (This stays a pure-Dart test — no path_provider / platform channels.)

## Out of scope / not changed

- vCard export/import — already fixed and verified.
- CSV **import** — already BOM-tolerant via the decoder; no change needed.
- Robustness against importing a *foreign* non-UTF-8 (Latin-1/ANSI) CSV:
  `readAsString()` would throw a `FormatException` on invalid UTF-8. This is a separate
  hardening item, not part of "keep our own data in Unicode"; noted here, not implemented.
- BLE / QR / P2P sync — in-app, app-to-app only, already UTF-8 via `utf8.encode/decode`.

## Verification

- `flutter test <the export/import test file>` — new BOM test passes.
- `flutter analyze` on the changed file — no issues.
- Manual: export contacts (with a Devanagari name) as CSV, open in Excel — name shows
  correctly; re-import the same CSV into the app — name round-trips, no stray BOM character.
