# Backup & Restore (password-protected, full DB + media)

**Status:** completed

## What the user wants

A "Backup / Restore" section in Settings.

- **Backup** — asks for a place to save a file, writes the whole app database (plus
  photos and calling-card images) into that file. The file must be openable by a
  *different* install of the app, even one signed with a different key, and even on
  another phone.
- **Restore** — asks for the backup file, then rebuilds the app data from it.

The user has chosen (confirmed in this session):

1. **Backup security = password-protected.** The user types a passphrase when making
   the backup; the file is encrypted with it. Restoring needs the same passphrase.
2. **Media = included.** Photos and calling-card images travel inside the backup.
   Ringtones are device-local and are skipped (same as the existing P2P sync).
3. **Restore mode = replace everything.** Restoring wipes the current data and rebuilds
   it as an exact copy of the backup.

## The core problem: the encrypted DB

The live database is encrypted with SQLCipher using a random 256-bit key that lives only
in the Android Keystore ([lib/database/db_key.dart](../lib/database/db_key.dart)). That
key never leaves the device and is destroyed when the app is uninstalled. So **copying the
raw `smart_contacts.db` file is useless anywhere else** — a re-install, a new phone, or a
differently-signed build can never read it.

**Therefore the backup must not depend on the Keystore key.** The fix is to re-protect the
data with something the *user* controls — a passphrase. The passphrase travels with the
user, so any install can restore. This is exactly how the app's own P2P sync already works
(a shared code derives the encryption key), so we reuse the same approach.

## What we reuse (little new "plumbing" is needed)

- **`SyncBundleService.exportBundle(mode: full)`**
  ([lib/services/sync_bundle_service.dart](../lib/services/sync_bundle_service.dart))
  already walks every shareable table, collects the settings, and stages every photo /
  calling-card file into an in-memory list with a manifest. Its output (a META JSON string
  + a list of media byte blobs) is Keystore-independent plain data — exactly the backup
  payload we need.
- **`cryptography` package (PBKDF2 + AES-GCM-256)** is already a dependency and is already
  used in [lib/services/p2p_sync_service.dart](../lib/services/p2p_sync_service.dart)
  (`Pbkdf2`, `AesGcm.with256bits()`, a random salt, a 12-byte nonce). We reuse the same
  primitives to encrypt the backup file with the user's passphrase. **No new package, no
  second SQLCipher database.**
- **File save / pick** — the app already saves exports with `SharePlus` (the share sheet
  lets the user pick "Save to Files" / Drive / a folder) and picks files with
  `openFile` from `file_selector`
  ([lib/services/export_import_service.dart](../lib/services/export_import_service.dart)).
  We follow the same proven pattern.
- **Auth gate** — the Sync hub is opened only after a biometric / device-lock check because
  the payload can include secret contacts (`SettingsScreen._openSync`). Backup carries the
  same secret data, so we gate the Backup/Restore screen the same way.

## The backup file format

A single file, suggested name `ContactSphere_Backup_<timestamp>.csbak`. Layout:

```
magic     : ASCII "CSBK" + 1 byte format version (= 1)
dbVersion : the schema version the backup was made at (so restore can check it)
salt      : 16 random bytes (for PBKDF2)
nonce     : 12 random bytes (for AES-GCM)
ciphertext: AES-GCM-256 seal of the PLAINTEXT BLOB below, key = PBKDF2(passphrase, salt)
```

The **plaintext blob** (before encryption) is a small self-describing binary container:

```
[uint32 metaLen][meta JSON bytes]                       <- exportBundle META JSON
then, repeated per media file:
[uint16 refLen][ref][uint8 extLen][ext][uint32 len][bytes]
```

The META JSON already lists the media manifest, so the reader knows how many media frames
to expect. This mirrors the P2P wire format (META first, then media frames) but written to
one file instead of a socket. A wrong passphrase makes the AES-GCM tag check fail, which we
turn into a clear "wrong password or corrupt file" error.

Notes / limits of this format (called out so they are deliberate, not surprises):

- **Schema version guard.** The backup stores its `dbVersion`. On restore, if it does not
  equal the current app's DB version, we refuse with a clear message ("This backup was made
  with a different app version…"), exactly like the sync guard does today. Restoring a
  backup across a schema change is **out of scope for v1** — documented as a known
  limitation.
- **Ringtones** (per-contact ringtone file paths) are not backed up — they point at
  device-local files. Same as sync.
- **`merged_device_ids`** (device address-book dedup bookkeeping) is not backed up — it is
  device-specific. Same as sync.
- Settings carried are the same portable subset the sync uses (`_syncedSettingKeys`);
  SIM-account-specific settings are intentionally excluded.

## Restore = replace everything

New logic (schema-aware, so it lives in `SyncBundleService` alongside the existing import):

`Future<void> replaceAllFromBundle(String metaJson, List<IncomingFile> media)`

1. Write the incoming media blobs into app storage; build a `ref -> local path` map
   (reuse the existing `_writeIncomingMedia`).
2. Open a DB transaction, `PRAGMA foreign_keys = OFF` for the duration (we are loading one
   self-consistent snapshot, so we insert rows verbatim with their original ids and keep
   foreign keys intact — no id remapping needed).
3. `DELETE FROM` every managed table.
4. Insert each backup row **verbatim**, only:
   - resolving `photo_path` / `card_photo_path` `@sync:<ref>` sentinels to the written file
     paths, and
   - forcing `ringtone_path = null`.
   `is_self`, `name_translit`, ids, and all other columns are preserved exactly (unlike the
   add-only *merge* import, which zeroes `is_self` and remaps ids). This is what makes the
   result an exact copy.
5. Re-enable foreign keys, commit.
6. Restore settings with `overwrite: true` (reuse `_restoreSettings`).

After a successful restore the UI returns to the contact list and forces a reload so the
replaced data shows immediately.

## New service: `BackupService`

`lib/services/backup_service.dart` — orchestrates password + container + file I/O and
delegates DB work to `SyncBundleService`.

- `Future<File> createBackup(String passphrase)`
  1. `exportBundle(mode: full)` → META JSON + media blobs.
  2. Build the plaintext blob, PBKDF2-derive the key from `passphrase` + a fresh salt,
     AES-GCM-seal it, prepend the header.
  3. Write to a temp file named `ContactSphere_Backup_<timestamp>.csbak`; return it (the
     screen then hands it to `SharePlus` so the user picks where to save).
- `Future<void> restoreBackup(XFile file, String passphrase)`
  1. Read the file, parse the header, derive the key, AES-GCM-open (wrong pass → clear
     error), parse the plaintext blob into META JSON + `IncomingFile`s.
  2. Check the stored `dbVersion` against the live DB version; refuse on mismatch.
  3. Call `SyncBundleService.replaceAllFromBundle(...)`.

## New UI: `BackupRestoreScreen`

`lib/screens/backup/backup_restore_screen.dart` — two `_SettingsCard`-style actions
matching the app's existing card design (its **own** design system, not a generic list):

- **Back up now** → password dialog (enter + confirm, minimum length, show/hide) → progress
  spinner → `SharePlus` save sheet → success snackbar.
- **Restore from a file** → `openFile` (accept `.csbak`; permissive fallback for Android
  SAF) → password dialog → a **strong** confirm dialog ("This deletes all current data and
  replaces it with the backup. This cannot be undone. Continue?") → progress → on success,
  pop to the contact list and refresh.

Small reused password-dialog widget (enter/confirm for backup, single field for restore).

## Risks / open points

- **Cross-version restore is not supported in v1** (schema guard refuses it). If the user
  wants backups to survive app updates, that is a follow-up (migrate the snapshot forward).
  Flag before building if this matters now.
- **Whole backup is held in memory** during encrypt/decrypt. Fine for a contacts app; if
  someone has thousands of large photos it could be heavy. Acceptable for v1.
- **Save location**: on Android the "choose a location" happens inside the `SharePlus`
  sheet ("Save to Files"), matching the app's existing exports. If you specifically want a
  native folder picker instead, `file_selector`'s `getSaveLocation` is the alternative —
  say so and I'll switch it.
