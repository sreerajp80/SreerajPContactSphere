# App-lock setting (require biometric unlock to open the app)

**Status:** completed

## What the issue is

The app already gates **secret contacts** and **sync** behind biometric/credential auth
(`AuthService`), and ships a biometrics help screen — but there is no way to require
authentication for the **whole app** on launch. A person who picks up an unlocked phone can
open ContactSphere and see all non-secret contacts, call history, etc. A whole-app lock is a
natural, expected setting given the privacy features already present.

## Plan for the fix

Add one persisted preference (`app_lock_enabled`), a lightweight lock screen shown on cold
start and when the app returns from the background, and a toggle in Settings. Reuse the
existing `AuthService` (no new native code, no new dependency).

### Preference (in `AppSettings`)

- `bool appLockEnabled` — key `app_lock_enabled` (bool), default `false`.
  Getter + `setAppLockEnabled()` + `load()` wiring, following the existing pattern.
- Add a `static Future<bool> readAppLockEnabled()` (like `readCallerIdEnabled`) so the
  lock gate can decide before the `AppSettings` instance finishes loading.

### Lock screen (new `lib/screens/app_lock_screen.dart`)

- A full-screen route with the app icon/name and an **Unlock** button that calls
  `AuthService().authenticate(reason: 'Unlock ContactSphere')`. On success it pops (returns
  `true`); it also triggers the prompt automatically on first show. It cannot be dismissed
  by the back gesture/button while locked (`PopScope(canPop: false)`).
- If `AuthService().isAvailable` is false (no device lock set up at all), the gate does **not**
  trap the user — it lets them in (same "can't authenticate, don't lock out" stance the sync
  gate already takes in `settings_screen.dart`).

### Lock gate (in `main.dart`)

- Make `_SmartContactsAppState` a `WidgetsBindingObserver`.
- On cold start (`_bootstrap`) and on `didChangeAppLifecycleState == resumed`: if app lock is
  enabled and not already showing, push the `AppLockScreen` over everything via `_navKey`.
- Track a `_locked` / `_lockRoute` flag so it is shown only once per lock episode.
- **Never** show the lock over a live call: if `_inCallRoute?.isCurrent` (the in-call screen),
  skip locking — mirrors the existing back-swipe guard.
- Mark "needs lock on next resume" when the app is `paused`, so returning from background
  re-locks (with a small grace so the biometric prompt itself, which backgrounds the app,
  doesn't cause a double lock).

### Settings UI

- Add an inline **App lock** switch card to the Settings hub (`settings_screen.dart`), placed
  near the top with the other security-adjacent items. Subtitle: "Require unlock to open the
  app". Toggling reads/writes `AppSettings.appLockEnabled`.
- If the device has no lock configured, the card explains it needs a device screen lock
  (disabled/greyed), consistent with the sync flow's handling.

## Files to be changed

- `lib/state/app_settings.dart` — `appLockEnabled` key + getter/setter + load wiring +
  `readAppLockEnabled()`.
- `lib/screens/app_lock_screen.dart` — **new** lock screen.
- `lib/main.dart` — lifecycle observer + lock gate (cold start + resume), in-call exclusion.
- `lib/screens/settings_screen.dart` — App lock toggle card.

## Out of scope (kept deliberately)

- A separate app PIN independent of the device credential (reuse device biometrics/PIN via
  `local_auth` only).
- A configurable auto-lock timeout (lock on every resume; a timeout can follow later).

## After implementation

Run `flutter analyze`, verify the lock shows on cold start and on resume (and never over a
live call), then write a change log to `change_log/` referencing this plan.
