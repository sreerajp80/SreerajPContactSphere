# Item 2, phase 2a — ARB localization infrastructure and pilot screen

**Plan:** `plans/20260921_064200_item2-arb-string-externalization.md` (phase 2a of 2a–2g)
**Status:** done. Phases 2b–2g are not started and need approval before any work begins.

---

## What this phase did

Set up ARB localization for the project and proved the whole loop on one screen.
Before this change the app had no `l10n.yaml`, no `lib/l10n/`, no `.arb` files and no
`AppLocalizations` anywhere; every user-visible string was an English literal inside a widget.

Now the machinery exists, three languages exist, and one screen —
`lib/screens/blocked_numbers_screen.dart` — reads every one of its strings from the ARB files.

No other screen changed. The other ~85 files that hold user-visible strings still hold English
literals, exactly as the plan phases it.

## Generated-file policy

Standard §12.2 requires the repository to declare one policy. This change picks **Option A —
generated files are committed**. `lib/l10n/app_localizations*.dart` are committed, so a fresh clone
runs `flutter analyze` and `flutter test` with no codegen step. `.gitignore` was not changed,
because it never excluded these patterns. Re-run `flutter gen-l10n` and commit the result after
editing any `.arb` file.

## Key naming convention adopted

The plan's step 2 suggested grouping keys by screen (`contactDetailTitle`). Standard §8.6 instead
asks for a **prefix** on every key, because the prefix is what makes the short-label budget
checkable by a script. This phase uses the §8.6 prefixes, with the screen name after the prefix:

| Prefix | Category | Budget |
|---|---|---|
| `action…` | buttons, menu items, dialog actions | short |
| `label…` | field labels, row labels, chips | short |
| `title…` | screen, app-bar and dialog titles | short |
| `tab…`, `nav…` | tabs and navigation destinations | short |
| `tooltip…` | tooltips on icon-only controls | short |
| everything else (`desc…`, `help…`, `empty…`, `error…`, `body…`, `hint…`, `msg…`, `aboutDetail…`) | descriptive prose | exempt |

"Short" means the §8.6 limits: 20 characters in English, 22 in Malayalam and Sanskrit, counted as
grapheme clusters. Every key added in this phase was checked by hand against those limits
(see "Open items" for the one that does not fit).

Two prefixes are not named in the standard's table and are used here as descriptive (exempt)
categories: `hint…` for text-field hints and `msg…` for snackbar confirmations. Worth adding to the
standard so other apps do not invent their own.

## Pilot screen: what it proves

`BlockedNumbersScreen` was chosen because it is small (297 lines) but exercises every mechanism the
remaining phases need:

- app bar title, dialog title, field label, field hint;
- two action buttons and one icon-only tooltip;
- an empty state and two blocks of explainer prose;
- a `String` placeholder (`msgNumberUnblocked`), an `int` placeholder (`labelBlockedCount`) and a
  date (`labelBlockedOn`);
- a snackbar raised from an async method, where `context` has to be captured before the `await`.

## Two things found while doing it

### 1. `intl` has no date or time data for Sanskrit

`labelBlockedOn` was first written as an ARB `DateTime` placeholder with `"format": "yMMMd"`, which
is the normal way and what standard §8.9 asks for. Under `sa` the generated code calls
`DateFormat.yMMMd('sa')`, and that **throws `ArgumentError: Invalid locale "sa"`** — the `intl`
package ships no CLDR data for Sanskrit.

Fixed here by formatting the date with `MaterialLocalizations.of(context).formatShortDate(...)` and
declaring `{date}` as a `String` placeholder. Material's formatter falls back cleanly on a locale it
does not localize, so the screen renders in all three languages today.

**This is bigger than this screen.** Every ARB `DateTime` placeholder, and every number or currency
placeholder that carries a `format`, will hit the same wall the moment Sanskrit becomes a real app
locale (item 1). Item 3 — `plans/20260921_064300_item3-sanskrit-fallback-delegates.md` — is the
right place to decide the project-wide answer: either register Sanskrit date and number symbols with
`intl`, or make a documented rule that formatted values are produced outside the ARB. Later phases
of item 2 should not add a `DateTime` or formatted-number placeholder until that decision is made.

### 2. The framework has no Material, Widgets or Cupertino localizations for Sanskrit

Pumping a `MaterialApp` with `Locale('sa')` fails: `GlobalMaterialLocalizations` does not support
`sa`, and the built-in `DefaultMaterialLocalizations` only covers `en`. This is the gap item 3
exists to close, and it is not fixed here.

So that §8.7's "test the screen in all three locales" could still be honoured now, the pilot test
file declares three small test-only fallback delegates that serve the English Material, Widgets and
Cupertino strings for any locale the framework does not localize. They sit last in the delegate
list, so `en` and `ml` keep their real framework translations and only `sa` falls through. They live
in the test file only — **nothing was added to `lib/`** — and they should be deleted once item 3
ships the real thing.

## Translations — needs native-reader review

Standard §8.5.4 says a new or changed Malayalam or Sanskrit term must be reviewed by a fluent reader
before an app uses it. Glossary terms were used as given. These are the ones **not** in the glossary,
which a reviewer should look at first:

| Key | English | Malayalam | Sanskrit | Why it is flagged |
|---|---|---|---|---|
| `labelPhoneNumber` | Phone number | ഫോൺ നമ്പർ | दूरभाषसङ्ख्या | The glossary says Number is `സംഖ്യ`, never `നമ്പർ`. That entry reads as "numeral" and does not fit a telephone number, so the everyday `നമ്പർ` was used. **Suggest adding "Phone number" to the §8.5.4 glossary** so every app agrees. |
| `actionBlock` | Block | തടയുക | निरुध्यताम् | Not in the glossary. Sanskrit is the passive polite imperative of `नि + रुध्`. |
| `titleBlockedNumbers` | Blocked numbers | തടഞ്ഞ നമ്പറുകൾ | निरुद्धसङ्ख्याः | Compound, nominative plural feminine. |
| `titleBlockNumber` | Block a number | നമ്പർ തടയുക | सङ्ख्यानिरोधः | Sanskrit uses the nominal form because it is a dialog title (§8.5 form convention). |
| `tooltipUnblock` | Unblock | തടയൽ നീക്കുക | विमुच्यताम् | `विमुच्यताम्` ("let it be released") chosen over a two-word phrase to keep the §8.6 one-word rule for Sanskrit actions. |
| `actionAddNumber` | Add a number | നമ്പർ ചേർക്കുക | सङ्ख्या योज्यताम् | Two words in Sanskrit (noun + imperative). §8.6 prefers one word; a single word that means "add a number" would have to be invented, so the standard phrase was kept. Reviewer should confirm. |
| `labelBlockUnknownCallers` | Block unknown callers | അജ്ഞാത കോളുകൾ തടയുക | अज्ञातसम्भाषकनिरोधः | `സമ്പർക്കകാരൻ`/`सम्भाषकः` for "caller" is not in the glossary. |
| `emptyBlockedNumbers` | No blocked numbers yet. | തടഞ്ഞ നമ്പറുകളൊന്നുമില്ല. | न काऽपि सङ्ख्या निरुद्धा। | Sanskrit agreement checked: `सङ्ख्या` is feminine, so `काऽपि` and `निरुद्धा` are feminine too. |
| `descBlockUnknownCallers`, `descBlockedNumbersInfo`, `descAddNumber`, `errorNotAPhoneNumber`, `msgNumberUnblocked` | (prose) | — | — | Full sentences. Sanskrit prose ends with a daṇḍa `।` per §8.5.1. Read for naturalness, not just correctness. |

The brand name "SreerajP Contacts Sphere" is left untranslated inside `descBlockedNumbersInfo` in
all three languages, which is intended.

## Open items this phase deliberately did not fix

1. **`labelBlockUnknownCallers` is 21 characters in English**, and the §8.6 short-text limit for
   English is 20. Malayalam (13) and Sanskrit (10) are comfortably inside the limit. Shortening the
   English switch label is a copy change, not a translation change, so it is left for a decision
   rather than done quietly. The obvious candidates are "Block unknown" (13) or "Unknown callers" (15).
2. **No `test/l10n/label_length_test.dart`.** Standard §8.6 sketches one and it would be cheap to
   add, but it would fail on the line above on its first run, so it is proposed rather than added.
   Worth adding in phase 2b together with whatever wording is chosen.
3. **The About-config group in the parity test is skipped.** `assets/config/app_config.json` still
   holds single-language prose and Title Case `details` keys ("AI used"), so the test's
   `aboutDetail<Key>` lookup cannot pass. The skip carries a comment naming phase 2g, which converts
   that file and deletes the skip.
4. **`supportedLocales` is still `en` and `ml`.** Adding `Locale('sa')` is item 1's job, as the plan
   states. `app_sa.arb` exists and is complete, but the running app cannot select Sanskrit yet.
