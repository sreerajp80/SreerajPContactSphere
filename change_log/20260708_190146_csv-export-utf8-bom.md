# Change log: CSV export writes a UTF-8 BOM (Unicode-safe in Excel/Sheets)

Implements plan `plans/20260708_190146_csv-export-utf8-bom.md`.

## Problem

The user asked to ensure all exported/imported data stays Unicode-safe. The vCard path
was already fixed (external `.vcf` uses vCard 2.1 with `CHARSET=UTF-8;ENCODING=QUOTED-PRINTABLE`
— see `change_log/20260707_205712_vcard-unicode-mojibake-export.md`). The **CSV export** was
the remaining gap: it used the default `Csv().encode(rows)`, which writes **no UTF-8 BOM**.
The file bytes are valid UTF-8 (`writeAsString` defaults to UTF-8), but with no BOM Excel /
Google Sheets on Windows fall back to the ANSI code page and show non-ASCII names (e.g.
Devanagari) as mojibake.

## Fix

Encode the whole-book / secret-book CSV with a UTF-8 BOM: `Csv(addBom: true).encode(rows)`.
The comma field delimiter is kept (not `Csv.excel()`, which would switch to `;` and collide
with the `;` we already use inside phone/email cells). The app's own re-import is unaffected:
the `csv` 8.0.0 decoder strips a leading BOM (`_checkBOMAndSep`), and the header row is
skipped on import anyway.

## Files changed

- **`lib/services/export_import_service.dart`**
  - `_writeAndShareCsv(...)`: `Csv().encode(rows)` → `Csv(addBom: true).encode(rows)`.
  - Expanded the method doc comment to explain the BOM and why import is unaffected.

- **`test/export_import_csv_test.dart`** (new)
  - Test 1: `Csv(addBom: true).encode(...)` output starts with the UTF-8 BOM and keeps the
    Unicode name as text.
  - Test 2: `Csv().decode(...)` round-trips the same content — the BOM does not leak into the
    first header cell and the Devanagari name survives unchanged.

## Verification

- `flutter test test/export_import_csv_test.dart` — both tests pass.
- `flutter analyze lib/services/export_import_service.dart test/export_import_csv_test.dart`
  — no issues.

## Not changed

- vCard export/import (already fixed and verified).
- CSV import decoding — already BOM-tolerant, no change needed.
- BLE / QR / P2P sync — in-app, app-to-app only, already UTF-8 via `utf8.encode/decode`.
- Importing a foreign non-UTF-8 (Latin-1/ANSI) CSV still throws on decode; noted as a
  separate hardening item, out of scope for this change.
