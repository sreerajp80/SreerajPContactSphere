# Change log — Backup & Restore (password-protected, full DB + media)

Implements plan [plans/20260711_002143_backup-restore.md](../plans/20260711_002143_backup-restore.md).

## What was added

A "Backup & Restore" section in Settings that saves the whole app database (plus
photos and calling-card images) into one **password-protected** file, and restores
it as a **full replace**. The file is portable: any install can restore it — even a
re-install, a new phone, or a differently-signed build — because it is encrypted
with the user's password, not the device Keystore key.

### The encrypted-DB problem, and how it is handled

The live DB is encrypted with SQLCipher using a random key kept only in the Android
Keystore (`db_key.dart`). That key dies on uninstall and cannot be read elsewhere, so
copying the raw DB file would produce a useless backup. Instead the backup re-protects
the data with a passphrase the user chooses (PBKDF2 + AES-GCM-256), reusing the exact
crypto primitives already used by the P2P sync (`p2p_sync_service.dart`). The passphrase
travels with the user, which is what makes the file portable.

## Files changed

**Added**
- `lib/services/backup_service.dart` — builds the encrypted backup and restores it.
  - `encodeBackup(passphrase)` → serializes the whole DB + settings + media via
    `SyncBundleService.exportBundle(full)`, frames it into a self-describing binary blob
    (meta JSON + media frames), then PBKDF2-derives a key from the passphrase + a random
    salt and AES-GCM-seals it. File layout: `"CSBK"` + version byte + salt + (nonce ‖
    ciphertext ‖ tag).
  - `createBackup(passphrase)` → writes `encodeBackup` to a temp `.csbak` file for the
    share sheet.
  - `restoreBytes` / `restoreBackup` → decrypt (wrong password → clear error), check the
    schema version matches, then full-replace. `BackupException` carries user-safe messages.
  - Encode/decode is kept free of `path_provider` so tests round-trip on the host VM.
- `lib/screens/backup/backup_restore_screen.dart` — the Backup/Restore UI: two cards, a
  password dialog (enter + confirm for backup, single field for restore), a strong
  "replace all data?" confirmation, and a busy overlay. On a successful restore it reloads
  `AppSettings` and pops to the home screen so lists refresh.
- `lib/screens/help/backup_help_screen.dart` — plain-English help article (what a backup
  holds, why the password matters, that restore replaces everything).
- `test/backup_service_test.dart` — round-trip (exact copy; original ids, `is_self`, and
  `name_translit` preserved; pre-existing rows removed; settings overwritten), wrong
  password rejected with no change, foreign/truncated file rejected, schema mismatch refused.

**Changed**
- `lib/services/sync_bundle_service.dart` — added `replaceAllFromBundle(metaJson, files)`:
  a FULL-REPLACE import (distinct from the existing add-only `applyBundle` merge). It wipes
  every managed table and reloads the snapshot verbatim — original ids, `is_self`, and
  `name_translit` preserved — resolving photo/card paths to freshly written files and
  dropping ringtone paths. Foreign keys stay ON; rows are deleted child→parent and inserted
  parent→child (added `_allManagedTables` for the ordering) because SQLite ignores
  `PRAGMA foreign_keys` inside a transaction.
- `lib/screens/settings_screen.dart` — added a "Backup & Restore" card, opened behind the
  same biometric / device-lock gate as Sync (a backup can include secret contacts) via a
  new `_openBackup`.
- `lib/screens/help/help_home_screen.dart` — added a "Backup & Restore" help topic card.

**No dependency changes** — `cryptography`, `file_selector`, `share_plus`, and
`sqflite_sqlcipher` were already present.

## Known limitations (as agreed in the plan)

- **Cross-version restore is not supported.** A backup made on a different DB schema version
  is refused with a clear message. Migrating an old snapshot forward is a future enhancement.
- Ringtones and `merged_device_ids` are not backed up (device-local), matching P2P sync.
- Settings carried are the same portable subset the sync uses (SIM-specific keys excluded).
- The whole backup is held in memory during encrypt/decrypt — fine for a contacts app.
